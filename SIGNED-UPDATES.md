# Signed application updates — 0.3.15

The first signed manifest is published for version 0.3.15 with metadata sequence 1. Older devices stay on the legacy `updates/stable.json` channel at 0.3.14 until explicitly enrolled. Historical releases/tags remain unchanged.

Publisher public-key SHA256: `34e43261378f0235107cc0d1e3eb8d2bed7d44c44d995323d7646203235dbfd0`.

## First step: create the publisher key on Windows

Use a trusted Windows PC, not the receiving Pi. Python 3 and the `cryptography` package are required. The tool works on Linux/macOS too.

```powershell
py -m pip install cryptography
py .\sign_release.py keygen
```

The tool prompts twice for a password and writes these files under your user profile's `.pisonde-signing` folder:

- `pisonde-release-private.pem`: encrypted PKCS8 private key. Keep this and its password private. Store an encrypted backup separately. Never upload it to GitHub, a chat, a receiving Pi or a workflow secret.
- `pisonde-release-public.pem`: public verification key. Safe to share and distribute. The tool prints its SHA-256 fingerprint over the DER public-key representation.

No production private key is generated by the project maintainer's assistant or in CI. The test suite generates throwaway temporary keys only. On Windows, keep the directory in your own protected user profile; Unix file mode 0600 does not configure Windows ACLs.

## Release and enrollment sequence

1. Share the public key and its printed fingerprint with the person preparing the release. Keep the encrypted private key and password on your computer.
2. Review the release's exact source commit and unsigned candidate manifest. Version 0.3.15 uses the explicit ten-file application allowlist. Source changes after this step require a new candidate and signature.
3. Download the reviewed candidate and sign it locally:

   ```powershell
   py .\sign_release.py sign .\candidate-0.3.15.json --sequence 1 --days 90 --output .\signed-stable.json
   py .\sign_release.py verify .\signed-stable.json --public-key "$HOME\.pisonde-signing\pisonde-release-public.pem"
   ```

   The tool displays the version, source commit, repository, sequence and expiry, then requires `SIGN` and the private-key password. Verification here proves the signature matches the supplied key; the receiving updater separately enforces policy, expiry, replay protection and file integrity.

4. Publish the signed manifest to `updates/signed-stable.json`, verify it using the independent public key, and publish the matching 0.3.15 tag/Release. The signed channel is published only after its signature has been independently verified. The public key is distributed at `updates/signing-public.pem`.
5. Enroll each existing Pi once through a separately verified enrollment installer. It must pin the supplied public key/fingerprint and install the reviewed verifier. A key fetched from a mutable repository without independent verification is not a trusted enrollment. Enrollment must verify the signature and code checksums before executing the replacement updater.
6. Enrolled devices use only the signed channel. Old 0.3.14 devices remain on the legacy channel until explicitly enrolled; they do not silently upgrade into a partially configured signed updater.

## Device enrollment

On an existing configured Pi, download `enroll-signed-updates.py` from the reviewed immutable release commit. Compare its SHA256 with an independently obtained value **before running it with sudo**. For this first installer the SHA256 is:

```text
602d94c2f2575ed666cccbce2b3a8c4e6c7363e3bf59bcf6c3ee272fa57ce76c
```

Run the verified installer with `sudo python3 /tmp/pisonde-enroll.py`. It pins the publisher key above, verifies the signed catalog before fetching executable code, verifies the updater's signed checksum, enrolls the public key, and runs the normal application backup/install/health workflow. A failed transition leaves the automatic-update timer stopped; resolve it before re-enabling updates.

Fresh installations must finish hardware/AP configuration first, then use the same enrollment step. Initial source installation and key enrollment are trust-establishment operations: do not accept an installer/fingerprint solely from a repository you suspect is compromised. The existing bootstrap entry point delegates to the hash-pinned enrollment installer, but verifying a downloaded bootstrap itself is still necessary for independent initial trust.

After enrollment, `/api/updates` reports `signatures_required: true`, `signing_enrolled: true`, and the accepted signing key ID. Confirm the version, key ID, timer/service state and RF reception on the device. No private signing key is needed by a receiving Pi.

## Security properties and limits

The exact signed bytes are an ASCII domain prefix plus sorted, compact JSON with `ensure_ascii=True`, excluding only the `signature` field. No third-party input controls the signature algorithm. Publisher signatures use Ed25519 via `cryptography`; the root updater verifies using `/usr/bin/openssl pkeyutl` and requires an Ed25519 public key. OpenSSL 3 support must be checked during enrollment.

The root-owned public key is stored outside application updates at `/etc/pisonde-mobile/update-signing-public.pem`. The updater never adopts a key from a downloaded manifest. It verifies the repository/channel, issuance/expiry, signature, monotonic metadata sequence and payload identity. It also retains the existing source-commit pin, exact file allowlist, per-file hashes, local backup and health checks. Verification occurs before staging and again before applying, including cached/offline updates. There is no unsigned fallback.

A root-owned `signature-state.json` remembers the highest accepted sequence and signed payload digest. Reusing identical metadata is allowed; older sequences or changed content at the same sequence are rejected. Re-sign renewed metadata with a strictly higher sequence, even when the application version is unchanged. Do not restore or delete this state as a way of bypassing a rejection.

The default metadata validity is 90 days. Renew it before expiry; expiry is an intentional stop to updates, not to radio reception. Clock errors can prevent updates. This is a single-key signed-manifest design, not a full implementation of The Update Framework. It does not promise availability if a repository attacker hides updates.

Key replacement/recovery is deliberately a manual, authenticated enrollment operation in this first revision, using an independently checked new fingerprint. Automatic key rotation and multi-key thresholds are not implemented. Losing the only private key requires operator re-enrollment with a new public key; losing only its password has the same effect unless it is recovered. A key supplied solely by a compromised GitHub repository must never be trusted as a replacement.
